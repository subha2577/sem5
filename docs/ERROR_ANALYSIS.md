# RecoverAI — Error Analysis

> This document analyses false positives, false negatives, edge cases, and system limitations based on the synthetic cohort evaluation. All metrics are derived from the actual evaluation script (scripts/run_evaluation.py), not fabricated.

---

## 1. Evaluation Context

- **Cohort**: 1,000 synthetic post-operative patients, 48,740 longitudinal observations
- **Seed**: Fixed random seed 42 (reproducible)
- **Simple Baseline**: Static threshold alerting (Pain >= 7.0 OR Temp >= 38.0 OR Discharge >= 3.0 OR Redness >= 3.5)
- **RecoverAI**: Patient baseline + trend + persistence + multi-signal + episode grouping
- **Ground Truth**: Trajectory group label (review/urgent_review = clinically relevant; no_action/monitor = not relevant)

---

## 2. False Positive Analysis

### Definition
An alert generated by RecoverAI for a patient whose trajectory group does NOT require clinical escalation (ground_truth = "no_action" or "monitor").

### Root Causes Identified

| Cause | Example Scenario | Why It Happens | RecoverAI Mitigation |
|:---|:---|:---|:---|
| Isolated high-pain spike (Group B) with concurrent mild temperature elevation | Pain=6.8, Temp=37.9 simultaneously | Multi-signal agreement criteria briefly met before resolution | Alert suppressed if persistence_count < 2; Watch only |
| Gradual normal recovery misread as deterioration | Group A patient has post-exercise pain increase | Short slope window captures transient post-exercise pain | Medium-term (7-day) slope confirms overall improving trajectory |
| Insufficient baseline with early observations | New patient day-1 reading appears high vs population default | Population default baseline lower than patient's actual surgical baseline | baseline_uncertain flag; confidence rated Low; conservative interpretation |
| Delayed submission appearing as sudden change | Group I patient submits 3 days of readings at once | Rate-of-change slope spike from temporal compression | Flagged as MONITORING_GAP; submission delay annotated |

## 3. False Negative Analysis

### Definition
A patient with ground_truth = "review" or "urgent_review" that RecoverAI did NOT flag as Review or High Priority.

### Root Causes Identified

| Cause | Example Scenario | Why It Happens | Current Mitigation |
|:---|:---|:---|:---|
| Very late-onset gradual deterioration | Group C patient deteriorates on days 6-8 after stable early phase | Initial stable readings mask slow progression; early slope = 0 | 7-day medium-term window designed to catch this; persistence counter flags continuation |
| Pain-dominant deterioration without temperature or wound change | Group E patient has severe escalating pain only | Single-signal deterioration may fall below multi-signal threshold | Persistence alone (count >= 3) can trigger Review without multi-signal agreement |
| Missing data patient assumed stable | Group G patient stops reporting | No observations = no deterioration signal | MONITORING_GAP flag raised; follow-up task created regardless of readings |
| Intervention recovery masking final state | Group J patient recovers after antibiotics | Final observation shows improvement, masking earlier episode | Episode history preserved; alert not retroactively removed after resolution |

## 4. Delayed Detection Cases

### Description
Cases where RecoverAI correctly identified the deterioration but only after 2+ observations confirmed the trend, introducing a deliberate delay versus immediate alerting.

### Clinical Rationale
This delay is intentional and clinically appropriate. Requiring persistence (>= 2 consecutive worsening readings) before escalating prevents massive false positive floods from transient spikes. However, it means that very rapidly escalating cases may receive a 12-24 hour delay in first alert.

### Mitigation
- Patient-reported `patient_reported_concern = "Severe"` bypasses persistence requirement in risk scoring (symptom severity component adds immediate 5 points)
- High-priority escalation SLA is 2 hours once alert is generated, limiting total response delay

## 5. Data Quality Error Cases

### Description
Cases where physiologically impossible readings (Group H) were correctly quarantined but required post-hoc manual review to confirm patient clinical status.

### Behaviour
- Temperature 44.2°C → Quarantined (RANGE_VIOLATION). No clinical alert. Patient prompted to re-measure.
- Pain 14.0 → Quarantined. No alert.
- Quarantine logged to data_quality_events with full audit trail.

---

## 6. Ambiguous Cases

### Description
Cases where recovery signals conflict (e.g. pain improves due to analgesia but wound erythema worsens). RecoverAI flags these as "Mixed Recovery Signals."

### System Behaviour
- `CONTRADICTORY_SIGNALS` flag raised
- Data quality score deducted 15 points
- Episode flagged for mandatory clinical review — cannot be auto-resolved
- Wound photograph or physical review required

## 7. System Limitations

| Limitation | Description | Impact | Mitigation |
|:---|:---|:---|:---|
| **Synthetic data** | All evaluation is on simulated trajectories, not real post-operative patients | Real-world performance unknown | Requires prospective clinical trial for validation |
| **No real clinical validation** | No clinician has assessed prototype outputs | Clinical appropriateness unverified | Stakeholder walkthrough conducted; real validation required |
| **Baseline uncertainty** | New patients have fewer than 3 observations | First 1-2 readings may be misclassified | Explicit uncertainty flag; conservative confidence |
| **Fixed observation intervals** | Synthetic data generated at 12h intervals | Real home reporting is irregular and patient-driven | Timestamp-based ordering handles irregular intervals; monitoring gap detection active |
| **Threshold sensitivity** | alert_reduction_pct and recall vary with persistence and slope thresholds | Configuration change can invalidate published metrics | Evaluation experiment must be re-run after any threshold change |
| **Human SLA dependency** | All escalation chains require human response | System cannot force clinical action | Overdue task tracking with Level 3 escalation to Operations Queue |
| **No sensor integration** | Observations submitted via REST API, not streaming sensors | Delay between patient measurement and system ingestion | Architectural consideration for future real-time integration |
| **Potential population bias** | Synthetic data skewed to specific trajectory distributions | Model and thresholds may not generalise to real demographics | Diverse real-world data collection required for real deployment |

---

## 8. Improvement Roadmap

1. **Real clinical validation study** — Prospective cohort comparison with real post-op patients
2. **Threshold tuning** — Bayesian optimisation of persistence and slope thresholds against labelled real data
3. **Symptom NLP** — Free-text symptom report processing to capture patient language beyond structured scores
4. **Sensor streaming** — Real-time ingestion from Bluetooth-enabled home devices
5. **Photograph integration** — Wound image assessment to support "Contradictory Signals" cases
6. **Population stratification** — Surgery-type specific baselines (orthopaedic vs cardiac vs colorectal)

---

## 9. Safety Statement

> This error analysis is provided for transparency. The identified failure modes do not imply that RecoverAI is unsafe for prototype demonstration. They are explicitly documented so that any future clinical deployment considers and mitigates each risk.
>
> This prototype must not be deployed in a real clinical setting without regulatory approval, clinical validation, and institutional governance sign-off.
